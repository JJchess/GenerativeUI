重要提示： 使用 官方 Google Gen AI SDK 并将完整的 模型回答对象直接附加到历史记录时，系统会自动处理思考签名。只有在使用 REST API 时，或者在多轮对话中手动提取和返回部分历史记录时，您才需要直接处理思考签名。

思考签名是模型内部思考过程的加密表示形式，用于在多步交互中保留推理上下文。 使用思考模型（例如 Gemini 3 和 2.5 系列）时，API 可能会 在回答的内容部分 中返回 thoughtSignature 字段（例如 text 或 functionCall 部分）。

一般而言，如果您在模型回答中收到思考签名，则应在下一轮中发送对话历史记录时，完全按收到的原样将其传回。使用 Gemini 3 模型时，您必须在函数调用期间传回思考签名，否则会收到验证错误 （4xx 状态代码）。这包括为 Gemini 3 Flash 使用 minimal 思考级别 设置的情况。

运作方式

下图直观地展示了“轮次”和“步骤”在 Gemini API 中与 函数调用相关的含义。“轮次”是用户与模型之间对话中的一次完整交流。“步骤”是模型执行的更精细的操作，通常是完成轮次的较大过程的一部分。

本文档重点介绍如何处理 Gemini 3 模型的函数调用。如需了解与 2.5 的差异，请参阅 模型行为部分。

Gemini 3 会为所有包含函数调用的模型回答（来自 API 的回答）返回思考签名。在以下情况下，系统会显示思考签名：

  • 如果存在并行函数 调用，模型回答返回的第一个函数调用部分将包含 思考签名。
  • 如果存在顺序函数调用（多步），每个函数调用都将包含一个签名，并且您必须传回所有签名。
  • 不包含函数调用的模型回答会在模型返回的最后一部分中返回思考签名。

函数调用部分中的签名

当 Gemini 生成 functionCall 时，它会依赖 thought_signature 在下一轮中正确处理工具的输出。

  • 行为：
    • 单个函数调用：functionCall 部分将包含 thought_signature。
    • 并行函数调用：如果模型在回答中生成并行函数调用 ，则 thought_signature **仅附加到第一个** functionCall 部分。同一回答中的后续 functionCall 部分将不 包含签名。
  • 要求：您必须 在传回对话历史记录时，在收到此签名的确切部分中返回此签名。
  • 验证：系统会对当前轮次中的所有函数调用强制执行严格验证。（仅需要当前轮次；我们不会验证之前的轮次）
    • API 会在历史记录中（从最新到最旧）查找包含标准内容（例如 text）（即当前轮次的开始）的最新用户 消息。这be 会是 functionResponse。
    • 所有模型 functionCall 轮次在该特定使用 消息之后发生，并被视为轮次的一部分。
    • 当前轮次每个步骤 中的第一个 functionCall 部分必须 包含其 thought_signature。
    • 如果您在当前轮次任何步骤中省略第一个 functionCall 部分的 thought_signature，请求将失败并显示 400 错误。
  • 如果未返回正确的签名，您将收到以下错误
    • Gemini 3 模型：如果未包含签名，将导致 400 错误。措辞将采用以下形式：
      • 内容块 <index of contents array> 中的函数调用 <Function Call> 缺少 thought_signature。例如，函数 调用 FC1 在 1. 内容块中缺少 thought_signature。

非 functionCall 部分中的签名

Gemini 也可能会在非函数调用部分的回答的最后一部分中返回 thought_signatures。

  • 行为：模型返回的最后内容部分（text, inlineData…）可能包含 thought_signature。
  • 建议：建议返回这些签名，以确保 模型保持高质量的推理，特别是对于遵循复杂指令 或模拟代理工作流的情况。
  • 验证：API 不 会严格强制验证。如果您省略它们，不会收到阻塞性错误，但性能可能会下降。

文本/上下文推理（无验证）

第 1 轮，第 1 步（模型回答）

{
  "role": "model",
  "parts": [
    {
      "text": "I need to calculate the risk. Let me think step-by-step...",
      "thought_signature": "<Signature_C>" // OPTIONAL (Recommended)
    }
  ]
}

第 2 轮，第 1 步（用户）

[
  { "role": "user", "parts": [{ "text": "What is the risk?" }] },
  {
    "role": "model", 
    "parts": [
      {
        "text": "I need to calculate the risk. Let me think step-by-step...",
        // If you omit <Signature_C> here, no error will occur.
      }
    ]
  },
  { "role": "user", "parts": [{ "text": "Summarize it." }] }
]

常见问题解答

  1. 如何将历史记录从其他模型转移到 Gemini 3，并在当前轮次和步骤中包含函数调用部分？我需要提供并非由 API 生成的函数调用 部分，因此这些部分没有关联的 思考签名？

    虽然强烈建议不要将自定义函数调用块注入到请求中，但在无法避免的情况下（例如，向模型提供有关客户端确定性执行的函数调用和回答的信息，或从不包含思考签名的其他模型转移跟踪记录），您可以在思考签名字段中设置以下虚拟签名 "context_engineering_is_the_way_to_go" 或 "skip_thought_signature_validator"，以跳过验证。

  2. 我正在传回交错的并行函数调用和回答，但 API 返回了 400。为什么？

    当 API 返回并行函数调用“FC1 + signature, FC2”时，预期的用户回答为“FC1+ signature, FC2, FR1, FR2”。如果您将它们交错为“FC1 + 签名, FR1, FC2, FR2”，API 将返回 400 错误。

  3. 在流式传输时，如果模型未返回函数调用，我找不到 思考签名

    在模型回答不包含具有流式传输请求的 FC 期间，模型可能会在包含空文本内容部分的部分中返回思考签名。建议您解析整个请求，直到模型返回 finish_reason。

不同模型的思考签名

Gemini 3 模型和 Gemini 2.5 模型 在函数调用中对思考签名的处理方式不同：

  • 如果回答中包含函数调用，
    • Gemini 3 将始终在第一个函数调用部分中包含签名。 必须 返回该部分。
    • Gemini 2.5 将在第一部分（无论类型如何）中包含签名。可以选择 返回该部分。
  • 如果回答中不包含函数调用，
    • 如果模型生成了思考，Gemini 3 将在最后一部分中包含签名。
    • Gemini 2.5 不会在任何部分中包含签名。

如需了解更多 比较详情 ，请参阅思考页面。对于 Gemini 3 Image 模型，请参阅 图片生成指南的思考过程部分。
